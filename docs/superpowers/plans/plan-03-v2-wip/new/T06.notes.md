## 2. Interfaces added beyond INTERFACES.md

All exports are in `src/lib/providerSwitchPlans.ts` unless noted.

- `export const ROUTE_PATCH_KEYS: readonly [...]`; `export type NonSecretKeys = (typeof ROUTE_PATCH_KEYS)[number]`; `export const ROUTE_PATCH_KEY_SET: ReadonlySet<string>`.
  - **Rationale:** INTERFACES names `NonSecretKeys` but does not define it. An explicit allowlist is the safest definition. It excludes every secret and also `dictationAgentVisionMode`, so "never writes vision mode" is enforced.
  - `applyRoutePatch` and `planPatch` throw on any key outside the list.
- `export const TRANSCRIPTION_CONTEXT_KEYS` (moved from `settingsStore.ts:58`), `export function defaultTranscriptionModel(providerId, context): string` (moved), and `export function reasoningModelBelongsToProvider` (moved; the store re-exports it for `OnboardingFlow.tsx:14`).

- `export function defaultCloudModel(providerId: string, options?: { vision?: boolean }): string`. The fallback for provider targets with no remembered model. Vision keeps only `supportsVision` cloud models.
- `export function resolvedScopeField(state, scope, field: "provider" | "model" | "cloudBaseUrl"): string`. The same fallback read as `selectResolvedLLMConfig`. It is needed because this module cannot import the store at runtime (the store imports it).
- `src/lib/routePlanner.ts`: `export const SETUP_AFTER_APPLY: ReadonlySet<string>` (codex plus enterprise).
- `planReasoningProviderSwitch` takes `scope: InferenceScope`, and `planTranscriptionProviderSwitch` takes `context: TranscriptionPolicyContext`. These are the same unions as INTERFACES' `LlmRouteScope` and `SttContext`, kept under the store's own names so the store never imports the route graph.
- `persistReasoningModelMemory` is removed, because it has no caller left. `applyRoutePatch` writes the memory JSON through a new `writeModelMemoryStorage(key, memory)` (localStorage only), so the whole patch is one `setState`. INTERFACES says "via persistTranscriptionModelMemory/persistReasoningModelMemory", but those functions each call `setState`, which would break the one-setState requirement. `persistTranscriptionModelMemory` stays for the onboarding seed (`:2432`).

## 4. Disputes and open issues

- **A coupled route can block the requested change.** The blocker is computed over every changed off-device route, as INTERFACES requires. So switching dictation to Groq while Note recording inherits dictation yields `blocker: "unsupported"`, because Groq is not a meeting streaming provider. That is safe, since it never silently breaks Note recording, but the user must first give Note recording its own provider.
  - **Alternative for the owner:** materialize the meeting or upload provider and model at their old values inside the patch when the change would otherwise break them. The review allows either approach.
  - I kept INTERFACES' rule and flag it here.
- **`kind` is stricter than the INTERFACES wording.** INTERFACES checks only `providerId` and `host`. The planner also requires the same `locality`, and it never treats an off-device route with an unknown host (`host === null` with `providerId` null or `custom`) as "same recipient".
  - Without this, a device→network change to an invalid URL would compare null/null and count as instant.
  - This is a strict tightening toward disclosure.
- **Enable flags.** Off routes never produce a blocker, because their state is `off`. Configuring an off route toward a provider without a key is therefore stageable and appliable. Turning the route on later (`useCleanupModel` and the other enable toggles) is not a planner change and starts sending immediately. That is outside Task 6's scope, but the owner may want enable toggles on an off-device route to go through review.
