## 1. Findings closed

- **I1 (store core).**
  - `requestRouteChange` classifies by the planner's `kind`, not by `target.mode`. Results on the device (including loopback endpoints and servers) commit instantly; any new off-device recipient or payload is staged.
  - Tests cover:
    - local→loopback endpoint (instant, with Undo);
    - loopback→remote (staged, nothing written);
    - another LAN server and provider→provider (staged);
    - a model-only change at the same provider (instant, which is the narrowing stated in HEADER's review table).
  - Apply re-plans from the live state at click time. It refuses with a blocker and keeps the draft, and a draft that is already satisfied becomes a no-op and is cleared.
  - Wiring the actual picker, endpoint and mode callbacks through `requestRouteChange` is Tasks 8–9.
- **I3.** `requestRouteChange` and `applyDraft` `await flushSecretSaves()` before planning. Tests hold main's acknowledgement with a deferred IPC promise and show that neither function plans or writes until the save is released. A draft discarded during the flush is not applied.
- **I14.** `currentPlanContext` reads `getSealed()` from `src/stores/sealedStore.ts` (Task 3) and facts from `useRouteFactsStore`. Nothing in this task reads sealed state from anywhere else. Tests seal through `useSealedStore` and show Apply blocked while device moves still apply.
- **I5 (Undo).**
  - Undo re-plans `plan.undoPatch` (the prior raw values, inheritance blanks and vision flags included) against the live state. It applies only an `instant` reverse; otherwise it stages a `kind: "patch"` draft, so Undo never moves work off the device without review.
  - A test shows remote→local→Undo staging the provider, and Apply then restoring provider and model exactly.
- **SET-Q10 copy.** `routeChangeMessage` names the destination with `providerDisplayLabel` (or the server host), says what is sent (`sends`), lists coupled routes, and tells off routes "will use X when you turn it on".

## 2. Interfaces added beyond INTERFACES.md

- `export function planDraft(draft: RouteDraft, copy: RouteCopy): RoutePlan` in `routeDraftStore.ts`. This is the live plan that Task 8's Apply bar renders and that `applyDraft` re-runs, so the bar and the click cannot disagree.
- New module `src/lib/routeChangeMessage.ts`:
  - `export type Translate = (key: string, options?: Record<string, unknown>) => string`;
  - `export interface RouteChangeMessage { title: string; description?: string }`;
  - `export function routeChangeMessage(plan: Pick<RoutePlan, "routeId" | "changes">, t: Translate, list: (items: string[]) => string): RouteChangeMessage`.
  - It takes the plan rather than one route so it can name coupled changes (I6), and `list` is `RouteCopy.list`.
- Outcome convention (within the INTERFACES type):
  - `applied: true` always has `blocker: null`;
  - a refusal is `applied: false` with a non-null blocker;
  - a no-op is `applied: false` with `blocker: null` and `plan.kind === "noop"`.
- Side effect kept from `InferenceConfigEditor.tsx:115-117`: when a committed patch sets any LLM scope mode to `"self-hosted"`, `commit` calls `window.electronAPI.llamaServerStop()`. Centralising it here means instant commits, Apply and Undo all behave the same, and Task 8 must not call it again.
- i18n keys `routes.toast.*` (12 keys, en block in the task). I assume Task 3 owns `routes.names.<RouteId>` and does not define `routes.toast`.

## 4. Disputes and open issues

- **Enable toggles bypass review.** Turning on an off route that already points off-device (`useCleanupModel`, `useDictationTranslation`, `useDictationAgent`, `voiceAgentScreenContext`) is not a provider, model or endpoint write, so it does not go through the planner. It starts sending at once. The owner may want these toggles to go through `planPatch` too (an allowlist extension in Task 6). Not done here.
- **Coupled blockers.** As noted in `T06.notes.md` §4, a coupled inherited route that would become unsupported blocks Apply of the requested change. Apply refuses with `"unsupported"`, and Task 8's bar must name the coupled route as the reason.
