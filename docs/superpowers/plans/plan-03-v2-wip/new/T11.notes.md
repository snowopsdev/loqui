# T11 notes — Keyring health in main

## 1. Findings closed

- **I11** — `verify(identity)` captures `credentials.generation(identity)` before `runTest` and records only if it is unchanged afterwards; otherwise returns `outcome: "superseded"` and writes nothing. Save/remove/undo/reset all bump the generation in the Task 2 authority, so they invalidate in-flight results. Concurrent Verify for the same identity+generation shares one request (coalesced via `inflight` map); a Verify after the key changed is a new request. Deferred-promise tests: replacement during Verify (the reproduced 401-on-replacement bug), removal during Verify (no row resurrection), two out-of-order verifications, coalescing, Verify-all (sequential `verify` over `list()`) interrupted by a replacement and a removal, reset during Verify.
- **I10 (keyring half)** — `provider_key_health` is keyed by `identity` (`corti:text`, `corti:speech`, …); `KeyringEntry.id` carries it and `RouteFacts.rejected` maps `entry.id` (Task 3 already does). `testConfigFor("corti:speech")` = `{ scope: "transcription", provider: "corti", clientId: "__stored__", clientSecret: "__stored__", environment, tenant }`; `corti:text` = `{ scope: "reasoning", provider: "corti" }`. The connection-test handler body is extracted verbatim into `_runProviderConnectionTest`; an IPC-level test runs it with a fake `this` and asserts the token request goes to `auth.<env>.corti.app/realms/<tenant>` with the stored client pair and never `"__stored__"`. A test shows a rejected Corti text key leaves Corti speech verified.
- **I3 (rejected-verdict case)** — the keyring subscribes to the authority: a save/undo that leaves an identity present resets its row to `unverified` (clears the error; restarts the rotation clock if a reminder is on); any change leaving it absent deletes the row. Every row change broadcasts `keyring-changed`; preload `keyring.onChanged`; `routeFactsStore` refreshes on it.
- v1 content kept: SQLite table (now `identity` PK), `classifyResult`, reminders via `i18nMain` + Electron `Notification` (now with the correct `const { i18nMain } = require("./i18nMain")` import that already exists at ipcHandlers.js:48; v1 suggested a default import that would have been wrong), PRIVACY.md row, browserPreview stub. Reminder loop now survives a throwing check (DB not initialized) and unrefs its timers. Keyring and reminders are created in the constructor, not `setupHandlers`, because several tests call `setupHandlers` on a fake `this` (granolaImportIpc, retryTranscriptionHandler) and a timer there would keep the test process alive.

## 2. Interfaces added beyond INTERFACES.md (INTERFACES only names the module)

- `createKeyring({ store, credentials, runTest, now, broadcast, isSealed })` → `{ list, verify, setReminder, takeDueReminders, dispose }`; exports `KEYRING_IDS`, `ROTATION_DAYS`, `testConfigFor(identity, options)`, `classifyResult`, `keyringDisplayName`, `startRotationReminders`.
- `KeyringIdentity` (12 verifiable identities; codex/bedrock/azure/vertex/custom slots have no keyring Verify because `testProviderConnection` has no endpoint for them), `KeyringEntry { id, providerId, status, lastVerifiedAt, lastErrorCode, lastErrorStatus, reminderDueAt }` (v1 had `provider`; `id` matches what T03 and T12 already assume; `providerId` added for `providerDisplayLabel`). The SQLite column is `identity`.
- `keyring.verify(identity, options?: { cortiEnvironment?, cortiTenant? }) → { outcome: "recorded" | "superseded" | "missing" | "sealed" | "invalidOptions"; entry }`. Options are needed because Corti's token endpoint depends on the renderer-held `cortiEnvironment`/`cortiTenant` (settingsStore `:1404-1405`); without them a non-US account would be verified against the wrong region. Invalid values are refused without a request (cortiAuth would otherwise throw "Invalid Corti …", which the test handler maps to `credentialsRejected`, ipcHandlers.js:1137-1149).
- `keyring.setReminder(identity, enabled) → KeyringEntry | null` (null when no key is stored).
- `keyring.onChanged(cb)`; broadcast `keyring-changed` `{ id }`.
- `isSealed` dependency (default `() => false`): CCR hook for Plan 07 to make main refuse Verify while sealed (`outcome: "sealed"`, no request). There is no main-side sealed state today (`grep sealed src/helpers` only hits secretCrypto).
- Uses Task 2 authority extras: `present(id)`, `generation(id)`, `subscribe(listener)` with `cause`.
- Verify all stays a renderer loop over `list()` (Task 12 shows per-item progress, v1 task09 `keyring.verifyingAll {current,total}`); no `keyring-verify-all` channel.
